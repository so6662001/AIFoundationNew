# 运维部署与监控告警（开发环境）

> 目标：`make up` 一键拉起 Temporal 开发集群 + PostgreSQL + Redis + 平台服务 + 监控告警；给出维护、备份、升级与生产迁移路径。

---

### 1.1 Temporal 关键配置

- Namespace：`agent-platform`，retention **7d**（开发）；生产建议 30d 并开启归档。
- `dynamicconfig/development.yaml`：
  - `limit.maxIDLength: 255`
  - `frontend.enableUpdateWorkflowExecution: true`（Update 能力）
  - `system.enableEagerWorkflowStart: true`
  - `history.defaultActivityRetryPolicy` 保持默认（业务重试由 DAG 控制）
  - `frontend.workerVersioningDataAPIs`/`WorkflowAPIs`: true（预留 Worker Versioning）
- Search Attributes：`FlowKey (Keyword)`、`FlowVersion (Int)`、`TriggeredBy (Keyword)`、`ParentRunId (Keyword)`。
- Worker 端：`max_concurrent_activities`（recon 默认 20，llm 队列 5）、`max_concurrent_workflow_tasks` 50；`sticky` 缓存开启。

### 1.2 PostgreSQL

- 开发期：单实例，`shared_buffers=512MB`，`max_connections=200`；三库分离便于日后拆机。
- 备份：`make backup` → `pg_dump` 三库到 `backups/<date>/`；Temporal 升级前必备份。
- `platform` 库迁移由 Alembic 管理；`temporal` 库 schema 由 `auto-setup` 初始化，升级用 `temporal-sql-tool update-schema`。
- 大表治理：`run_events` 按月分区，保留 30 天；`artifacts.inline` 超过 5 MB 的强制走 MinIO（生产）。

## 2. 监控指标

### 2.1 Temporal Server（`temporal:8000/metrics`，官方 Grafana 看板）

| 指标 | 关注点 |
|---|---|
| `service_requests` / `service_errors` | Frontend 请求错误率 |
| `persistence_latency` | PG 持久层延迟（P95 > 200ms 告警） |
| `workflow_task_schedule_to_start_latency` | **Worker 不足 / 掉线**信号 |
| `activity_schedule_to_start_latency` | 节点队列积压（按 task queue） |
| `workflow_failed` / `workflow_timeout` / `activity_task_error` | 失败趋势 |
| `history_size` / `history_count` | History 膨胀（坑 3 的量化监控） |

### 2.2 SDK / Worker（`:9464/metrics`）

| 指标 | 关注点 |
|---|---|
| `temporal_workflow_task_replay_latency` | 回放耗时（解释器复杂度） |
| `temporal_workflow_task_execution_failed` | **非确定性错误**（`NonDeterminismError`）→ 立即 P1 告警 |
| `temporal_activity_execution_failed{activity_type}` | 节点失败 |
| `temporal_activity_execution_latency{activity_type}` | 节点耗时 |
| `temporal_worker_task_slots_available` | Worker 饱和 |
| `temporal_sticky_cache_hit/miss` | 缓存效率 |

### 2.3 平台自定义（`platform-api:8000/metrics`，由 projector 打点）

| 指标 | 说明 |
|---|---|
| `platform_runs_total{flow_key,status}` | 运行数 |
| `platform_run_duration_seconds{flow_key}`（histogram） | 流程耗时 |
| `platform_node_duration_seconds{flow_key,node_id,node_type}`（histogram） | 节点耗时 P50/P95 |
| `platform_node_failed_total{flow_key,node_id,node_type,error_type}` | 节点失败 |
| `platform_node_retries_total{...}` | 重试次数 |
| `platform_approval_pending{flow_key}` / `platform_approval_wait_seconds` | 审批积压与时长 |
| `platform_run_context_bytes{flow_key}`（gauge/hist） | 上下文大小（坑 3） |
| `platform_llm_tokens_total{profile,node_type}` / `platform_llm_cost_usd_total` | LLM 用量成本 |
| `platform_sse_clients` | 实时连接数 |
| `platform_worker_online{task_queue}` | 注册中心视角的 Worker 在线数 |

## 3. 告警规则（Prometheus `alerts/*.yml` + 事件驱动）

| 告警 | 条件 | 级别 | 通道 |
|---|---|---|---|
| `TemporalDown` | `up{job="temporal"} == 0` 1m | P1 | IM + 电话（生产） |
| `NonDeterminismDetected` | `increase(temporal_workflow_task_execution_failed{failure_reason=~".*NonDeterminism.*"}[5m]) > 0` | P1 | IM |
| `WorkerOffline` | `platform_worker_online{task_queue} == 0` 2m 或 `workflow_task_schedule_to_start_latency` P95 > 10s 5m | P1 | IM |
| `ActivityBacklog` | `activity_schedule_to_start_latency` P95 > 60s 5m | P2 | IM |
| `NodeFailureRateHigh` | 某 `node_type` 15m 失败率 > 20% 且样本 ≥ 5 | P2 | IM |
| `NodeFailedPaused`（事件驱动） | projector 收到 `node.failed` 且 `onError=pause` | P2 | IM（带运行链接、节点、错误摘要、"去处理"按钮） |
| `ApprovalOverdue`（事件驱动） | `approval.reminder` / 待审批超过 `timeout` 的 50% | P3 | IM 提醒审批人 |
| `RunContextLarge` | `platform_run_context_bytes` > softLimit | P3 | IM |
| `PersistenceSlow` | `persistence_latency` P95 > 200ms 5m | P2 | IM |
| `PostgresDiskHigh` / `RedisMemoryHigh` | 使用率 > 80% | P2 | IM |
| `LLMCostSpike` | 1h 成本 > 阈值 | P3 | IM |

- Prometheus 告警 → Alertmanager → 企业微信 / 钉钉 webhook（使用 `prometheus-webhook-dingtalk` 或自建 `alert-bridge`，统一模板）。
- 事件驱动告警由 `platform-projector` 直接调用同一 `alert-bridge`，保证消息格式一致、带可点击运行链接。
- 抑制与聚合：同一 `flow_key + node_id` 5 分钟内合并；维护窗口静默。

## 4. Grafana 看板

1. **Temporal Server**（官方 `server-general`、`server-persistence`）。
2. **Temporal SDK**（官方 `sdk-general`：Worker slots、任务延迟、失败）。
3. **Agent Platform 总览**：运行数 / 成功率 / 进行中 / 待审批 / P95 耗时 / 最近失败列表（点击跳监控页）。
4. **流程明细**（变量 `flow_key`）：节点耗时热力图、失败率、重试率、分支命中分布、审批时长。
5. **LLM 用量**：token、成本、延迟按 profile / node_type。
6. **基础设施**：PG、Redis、容器资源。

## 5. 日常维护 Runbook

| 场景 | 操作 |
|---|---|
| Worker 升级 | 滚动重启（多副本）；解释器逻辑变更必须带 `workflow.patched`；先 `make test-replay` |
| Temporal 升级 | 备份 PG → 按官方顺序升 schema（`temporal-sql-tool`）→ 升镜像；单跳一个 minor |
| 清理运行数据 | `run_events` 分区 drop；artifacts 过期清理任务（`expires_at`）；Temporal retention 自动 |
| 卡住的运行 | Temporal UI 查看等待的 Signal / Activity；用 `POST /runs/{id}/nodes/{n}/actions` 处置；极端情况 `temporal workflow reset` 到指定事件 |
| 非确定性告警 | 立即回滚 Worker 镜像；用 History 回放定位；修复后加 patch 重新发布 |
| 密钥轮换 | Worker 环境变量 / Vault；DAG 只含 `credentialRef`，无需改流程 |

## 6. 安全基线（开发环境即执行）

- Temporal gRPC 仅内网；Temporal UI 加反向代理 Basic Auth / SSO。
- platform-api：JWT（内部）+ API Key（开放）；CORS 白名单。
- 密钥不进 DAG、不进日志（SDK 脱敏）；`.env` 不入库，提供 `.env.example`。
- 容器只读根文件系统、非 root 运行。

## 7. 生产迁移路径（不在阶段 1/2 范围，提前留口）

| 项 | 开发 | 生产 |
|---|---|---|
| Temporal | auto-setup 单容器 | 官方 Helm：frontend/history/matching/worker 各 ≥ 2 副本；PG 主从或云 RDS；可见性可用 PG（≤ 数百万 workflow）或 Elasticsearch |
| 平台 DB | 单 PG | 云 RDS + 读副本；`run_events` 可迁 ClickHouse |
| 事件总线 | Redis 单机 | Redis Sentinel/Cluster 或 Kafka |
| Artifact | PG bytea | S3/MinIO + 生命周期 |
| Worker | compose 副本 | K8s Deployment + HPA（按 `task_slots_available` / 队列延迟） |
| 部署 | compose | Helm + ArgoCD；镜像 SBOM 扫描 |
| 告警 | 企业 IM | IM + 电话值班（P1） |
